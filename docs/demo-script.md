## 链路一：订单延迟异常闭环（供应链域）

**目标**：展示"规划 → 调度 → 执行 → 审批 → 完成"的最小闭环，以及可视化打分依据。

1. 工作台 → 快捷发起 → 选「订单延迟异常闭环」，优先级 `1`、复杂度 `5`、数量 `420` → 发起任务。
2. 自动跳转任务详情，讲解右侧三块：
   - **策略 / 规划者 / 总分**：当前 `s4_llm_planner`，由大模型规划器提出候选；
   - **执行智能体**：`express-triage`（快线大模型）——因为它要满足"高优先级 + 高复杂度"；
   - **因子条形图**：能力匹配 0.500、历史成功率 0.485 的贡献；
   - **被淘汰的候选**：4 个智能体因缺少 `order_query` / `impact_assess` 被硬过滤。
3. 点「查看运行」→ 时间线依次出现 `start → fetch_order → assess_impact → evaluate → gate`，停在 `approve_remedy`（待审批）。
4. 点右上「通过」→ 2 秒内补上 `notify → end`，状态变为成功，显示耗时与成本。
5. 回到工作台，KPI 的成功率随之更新。

**可讲的点**：`evaluate` 节点的执行者不是写死的，而是由调度决策解析（`resolved_by: dispatch:s4_llm_planner`）。

## 链路二：区域履约诊断与整改（供应链）

**目标**：证明矩阵能处理"批量结构性问题"——不只是单张订单，而是某个地区整体的履约质量。

1. 左侧「智能体矩阵」→ 展示 6 阶段 × 4 能力的覆盖率（当前 75.0%，18/24），指出 6 个能力缺口；
   每个阶段名下方标注产业关联度（影 / 感），说明行的划分有数据依据。
2. 工作台 → 发起 → 工作流选「区域履约诊断与整改」，地区填 `Western Europe`（留空则自动选最差地区）。
3. 任务详情：派给 `fulfillment-analyst`，理由由真实模型给出（会写"唯一候选，能力完全匹配"这类判断）。
4. 运行详情看三步真实数据：
   - `region_stats`：10,010 单，准时率 17.01%，延迟率 55.79%，平均延迟 0.591 天，并给出地区排名；
   - `segment`：按运输方式拆开——Second Class 延迟率 77.27%、First Class **95.35%**、Same Day 47.07%、Standard Class 38.88%；
   - `diagnose`：真实模型（DeepSeek）输出结论 + 依据 + 三步整改方案，会引用具体数字。
5. `gate` 判断最差环节延迟率 ≥ 50% → 进入审批；通过后 `issue` 生成《履约整改单.md》。
6. 在「产物」卡片点「下载」，得到完整 markdown（现状 / 薄弱环节 / 整改方案）。

**可讲的点**：

- 诊断结论不是模板：同一套流程换个地区，模型会给出不同判断（First Class 那 95% 的延迟率就是它自己发现的）；
- 数据全部来自真实订单表，`region_stats` 与 `segment` 的数字可以在「可视化」页交叉核对；
- "批量问题 → 定位薄弱环节 → 审批 → 整改单" 是供应链运营的标准动作，比单订单处理更能体现矩阵价值。

## 链路三：运行详情与工作流图

1. 任意运行详情页顶部是**工作流图**：`start → fetch_order → assess_impact → evaluate → gate → approve_remedy → notify → end`。
2. 节点颜色即执行状态：绿色成功、橙色待审批、灰色未执行；条件分支边上标注 `真/假`。
3. **点图上的节点**，下方时间线会自动展开该节点的输入输出并高亮——图和轨迹是联动的。
4. 颜色会随运行推进实时变化（页面每 2 秒轮询）：审批通过后 `notify`、`end` 会由灰转绿。

**可讲的点**：图是从工作流版本的定义实时渲染的，不是截图或硬编码；同一份定义既驱动执行引擎，也驱动可视化，避免"图与实际行为不一致"。

## 链路四：监控仪表盘（管理者视角）

1. 左侧「仪表盘」→ 一屏看到：运行总数、成功率、**P95 执行耗时**、累计成本。
2. 重点解释两个耗时口径：
   - **执行耗时**（P50 41ms / P95 231ms）：引擎与技能的真实开销；
   - **端到端耗时**（P95 37s）：含人工审批等待。
   - 分开报的原因：审批慢不该被误读成引擎慢。这是答辩时容易被追问的点。
3. 运行趋势图（按小时堆叠）、智能体调用分布、按工作流统计、最近失败。

## 链路五：故障注入 → 重试 → 死信 → 人工恢复

**目标**：展示错误分类、指数退避重试、死信队列与人工接管——这是工程深度最集中的一段。

一条命令跑完整演练：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-test.ps1
```

手工演示（订单号里带标记即可触发故障注入）：

| 订单号 | 行为 | 观察点 |
|---|---|---|
| `SO-FLAKY-001` | `notify` 前两次失败，第三次自动成功 | 运行详情里 `notify` 出现 3 条记录，前两条红色 `TRANSIENT`、状态 retrying |
| `SO-DEAD-001` | `notify` 连续 3 次失败 → 进入死信 | 「死信队列」出现一条，错误分类 `TRANSIENT`、尝试次数 3 |

死信页点「重试」→ 运行回到失败节点重新执行（第 4 次尝试成功）→ 死信状态变为 `retried`。

**可讲的点**：

- 只对 `TRANSIENT / RATE_LIMIT / UPSTREAM / TIMEOUT` 重试；`VALIDATION / BUSINESS / PERMISSION` 直接失败，不浪费模型调用。
- 退避是指数 + ±20% 抖动，重试任务带 `next_attempt_at`，到点前 Worker 不会领取。
- 死信与失败状态在同一次事务提交，外部不会看到"已失败但没有死信"的中间态。

## 链路六：告警

**目标**：展示"规则可配置、事件可确认、恢复可自动"的闭环。

1. 先制造一个待处理死信（见链路四的 `SO-DEAD-xxx`）。
2. 打开「告警」页 → 30 秒内（或点「立即评估」）出现一条 `严重` 级事件：`死信积压：待处理死信数 当前 1 > 阈值 0`。
3. 点「确认」→ 状态变 `已确认`（表示有人接手），再点「恢复」→ `已恢复`。
4. 演示自动恢复：在「死信队列」点「忽略」→ 回到告警页点「立即评估」→ 系统会输出"恢复「死信积压」"。
5. 演示规则开关：停用「审批积压」→ 该规则不再产生事件。

**可讲的点**：

- 规则是数据（指标 + 比较符 + 阈值），不是可执行表达式，天然避开了注入风险。
- 同一规则在同一时刻只有一条未关闭事件（去重），避免刷屏。
- 条件恢复后自动关闭事件，人工只需处理"还在发生"的问题。

## 链路七：工作流设计器

**目标**：证明工作流不是硬编码的，可以改、可以校验、可以版本化。

1. 左侧「工作流」→ 列出两条链路 → 对「订单延迟异常闭环」点「打开设计器」。
2. 点画布上的 `gate` 节点 → 右侧出现条件表达式与真假分支配置。
3. 点「+ 技能」新增节点 → 点「校验」→ 底部报出 `技能节点未指定 skill`（错误）与 `节点 node_9 从入口不可达`（警告）。
4. 填写技能编码、用「连线」把它接入流程（先点起点再点终点）→ 再次校验通过。
5. 节点可直接拖动调整位置（坐标随版本保存，不影响执行语义）。
6. 选好「版本对比」的 from/to → 点「对比」→ 列出节点增删、字段变化、连线增删。
7. 点「保存为新版本」→ 生成新版本，**旧版本仍保留**，正在运行的任务不受影响；新建任务自动使用最新版本。

**可讲的点**：

- 校验在服务端做，保存失败会返回结构化错误（带节点 id），前端直接定位。
- 已发布版本不可变：改图是新建版本，不是原地修改——这是"运行可复现"的前提。
- 条件表达式是受限语法（比较 / in / 空值判断），不做 `eval`。
- 版本对比忽略布局坐标，挪动节点不会被误报为语义变更。

**当前未实现（如实说明）**：撤销/重做、节点复制粘贴、自动布局算法。

## 链路八：在 DSH 对话里发起任务（跨系统闭环）

**目标**：证明工作台不只是网页应用——DSH 里的智能体可以用自然语言驱动它。

**前置**：`dev up` 且后端 healthy；插件已加载（设置 → 插件里 `dsh-agentmatrix-tools` 为启用）。

1. **新开一个 DSH 对话**（老会话的工具清单不会刷新）。
2. 输入：

   > 用 agentmatrix_create_task 给订单 100 建一个延迟异常任务，优先级 1

3. 观察工具调用卡片：`agentmatrix_create_task`，参数含 `task_title`、`workflow_code`、
   `payload.order_id = 100`。
4. 工具返回里能看到：`assigned_to`（派给谁）、`strategy`（策略）、`score`、
   `top_factors`（打分拆解）、`rejected`（被淘汰的候选）。
5. 若带了 `wait_seconds`（默认 8 秒），返回里还有 `run.status` 与 `run.steps`——
   这次会停在 `waiting_approval`，并给出 `pending_approval_id`。
6. 切回工作台「工作台」页 → 第一行就是这条新任务，状态「待审批」→ 点「通过」→ 运行继续跑完。

**可讲的点**：

- 工具是通过 Cordis 插件注册的（`inject: ['tools']`），不是硬编码的快捷按钮；
- 模型自己决定调哪个工具、填哪些参数，插件只负责把它们翻译成 API 调用；
- 后端日志能看到 `POST /auth/login` + `POST /tasks`，来源是宿主机网关（插件），
  与浏览器流量（web 容器）可区分——调用链路可追溯。

**已知限制**：工具只读与建任务，**没有"通过审批"的工具**——审批必须回到工作台点，
这是有意为之（自动审批会让"人工卡点"失去意义）。

## 答辩时可能被追问的三个问题

| 问题 | 现场演示 |
|---|---|
| 「这条运行为什么分配给这个智能体？」 | 任务详情页的打分拆解 + 淘汰原因 |
| 「审批超时/驳回会怎样？」 | 运行详情点「驳回」→ 运行直接 failed，错误码 `APPROVAL_REJECTED`；任务状态同步为失败 |
| 「上游一直失败怎么办？」 | 订单号带 `DEAD` 触发故障注入 → 3 次重试后进死信 → 人工重试恢复 |
| 「关掉网络、不配 API Key 还能跑吗？」 | 把 `LLM_PROVIDER` 切回 `mock` 即可离线跑完全部链路；当前默认用 DeepSeek 真实模型 |
