# 设计指南：技能、能力、智能体、策略

> 面向需要在平台上新增能力的场景：技能设计、注册、挂载到智能体，
> 以及策略选型与调参。平台内同一内容另有页面：`/guide`。
>
> **当前规模（2026-11-23）**：种子技能 15 个、种子智能体 15 个（演示库当前各 34，含界面/E2E 新建）；调度策略 5 条（S0–S4）。

## 1. 四个概念的关系

```
技能（能做什么）──绑定──▶ 智能体（谁来做 + 能力标签）──编排──▶ 工作流（按什么顺序做）──发起──▶ 任务（按能力路由）
```

概念对照：

| 概念 | 回答的问题 | 关键字段 | 失效表现 |
|---|---|---|---|
| 技能 | 能做什么 | `input_schema` / `config` | 试运行报错、参数对不上 |
| 能力标签 | 该执行者可以承接哪些任务 | `agents.capabilities` | 任务硬过滤淘汰全部候选 |
| 智能体 | 谁来做、用什么提示词和模型 | `agent_versions.system_prompt` / `skill_ids` | 派给了但输出不对 |
| 策略 | 在合格候选里挑谁 | `system_settings.dispatch` | 成本高 / 稳定性差 |
| 工作流 | 按什么顺序做 | `graph.nodes` / `required_capabilities` | 图校验失败、节点报错 |

**最容易混淆的一对**：能力标签决定任务能否路由到该执行者，技能是该执行者的实现方式。
任务只认能力标签；技能只是智能体用来完成工作的工具。名字可以一样（都用 `carrier_quote`），含义不同。

## 2. 注册一个能力：四步

以"承运商报价"为例。

### 第 1 步：写技能（`/skills` → 新建技能）

- 类型选 **HTTP**，配置 `mock: true`（离线演示：不联网、无需 Key，响应按 `mock_response` 模板返回）；
- 输入 Schema 决定试运行表单，字段名要贴合业务：

```json
{
  "carrier": { "type": "string", "required": true, "label": "承运商" },
  "weight_kg": { "type": "number", "label": "重量(kg)" }
}
```

- 建好后在详情页**先试运行**：查看响应、耗时与错误码；失败时可见错误分类（如 `TRANSIENT`）。

### 第 2 步：建智能体并绑技能（`/agents` → 新建智能体）

- 系统提示词写"角色 + 输出要求"，不写入业务数据（数据来自技能）；
- 绑定技能后，**能力标签会自动带上同名编码**（可以改）；
- 新建是草稿，先在详情页**在线测试**：轨迹里会逐个执行绑定技能，再调模型。

### 第 3 步：在流程里用它（`/workflows`）

- 技能节点 = 直接调技能；智能体节点 = 交给"被调度选中的智能体"（`agent_code: "$dispatch"`）；
- 工作流级 `required_capabilities` 决定该任务所需的执行者能力。

### 第 4 步：发任务，看打分（工作台 / `POST /tasks`）

任务详情中可查看：派给哪个执行者、六个因子的贡献，以及被淘汰候选的原因。
若全部被淘汰，原因通常为"缺少能力 xxx"，需回到第 2 步补充能力标签。

## 3. 策略选型

| 场景 | 策略 | 代价 |
|---|---|---|
| 日常生产 | 加权打分（S2，产品基线） | 无明显代价，可解释性最好 |
| 降本压力大 | SLA 约束下的成本优先 | 成功率可能下降 |
| 关键任务 | 全大模型（基线） | 成本与时延显著上升 |
| 论文对比 | 五种都跑 | — |

> 当前实现 5 条策略：S0 `s0_all_large` / S1 `s1_fixed_rule` / S2 `s2_weighted`（加权打分，产品基线）/ S3 `s3_cost_aware` / S4 `s4_llm_planner`。
> 注意：代码里的默认值（`config.py`）是 S2，但 `.env.example` 把默认策略设成了 S4；实际生效值以 `/settings/dispatch` 页显示为准（当前开发机为 `s4_llm_planner`）。

## 4. 策略调参（`/settings/dispatch`）

**改 → 试算 → 保存**，三步闭环：

1. 拖权重滑块（六个因子之和不必等于 100%，系统按总和归一）；
2. 选一个工作流，点"用当前草稿试算"——用真实候选集跑一次打分，不调模型、不落库
   （当前策略为 S4 时，试算仍使用规则近似规划器，避免每次试算都触发模型调用）；
3. 排名符合预期再保存。保存写 `system_settings`，**下一次调度立即生效**，Worker 不用重启；
4. 每次修改都进审计（`dispatch.configure`，记录改前/改后）。

权重设计经验（来自本项目实验）：

- 能力匹配 35% 是底线：派错执行者后，成功率与成本指标均失去意义；
- 成功率 20% 与成本 10% 之间是"质量—成本"权衡，压成本时先动这两项；
- 负载 15% 用于削峰，单机演示看不出差别，并发压测时才明显；
- 亲和 10% 让高优先级任务偏向强模型，低优先级偏向便宜模型。

## 5. 四个常见设计问题

1. **能力标签 ≠ 技能编码**：名字可以一样，但一个用于调度、一个用于实现。
2. **技能未绑定到智能体即不生效**：技能列表里"被引用 0"即为信号。
3. **工作流要求的能力必须有智能体声明**，否则硬过滤淘汰所有候选，任务停在 pending。
4. **变更需发布版本**：技能改配置、智能体改提示词都生成新版本；运行锁定版本，草稿不影响线上。
